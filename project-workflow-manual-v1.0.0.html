1. โครงสร้างพื้นที่จัดเก็บ

หลักการ: ต้นฉบับไม่เคยถูกเขียนทับ → เพิ่มรุ่นใหม่เมื่อมีการเปลี่ยน → เก็บทุกเวอร์ชัน ไม่ลบ

ไดเรกทอรี วัตถุประสงค์ กฎการใช้งาน สิทธิ์เขียน เก็บรุ่น
00_CONTROL/ กติกากลาง, แบบฟอร์ม, คำจำกัดความสถานะ, ขั้นตอนมาตรฐานระบบ อ่านอย่างเดียว — ห้ามแก้ไขโดยไม่มีการอนุมัติและบันทึกเหตุผล readonly true
01_INBOX/ บันทึกโจทย์ผู้ใช้ตามถ้อยคำเดิม; เก็บไฟล์และเอกสารต้นฉบับที่ได้รับ คัดลอกข้อความตรงตัว ห้ามแก้ไข ตีความ หรือสรุปแทนเจ้าของข้อความ บันทึกเวลาและแหล่งที่มาทุกรายการ append true
02_EVIDENCE/ เก็บข้อมูลดิบ ผลสืบค้น เนื้อหาเอกสารต้นฉบับ พร้อมแหล่งอ้างอิง รุ่น และวันที่เข้าถึง ข้อมูลทุกรายการต้องระบุแหล่งที่มา รุ่นหรือหมายเลขฉบับ และวันที่ หากไม่มีแหล่งอ้างอิงที่ยืนยันได้ ให้ระบุสถานะ NOT_FOUND append true
03_WORK_PACKAGES/ แยกเก็บงานย่อยตามส่วนงาน แต่ละรายการประกอบด้วยรหัสงาน โจทย์ย่อย รายการที่ต้องทำ ผลลัพธ์ระหว่างทาง และปัญหาที่พบ ทุกไฟล์ต้องมีรหัสงานกำกับ หนึ่งไฟล์ต่อหนึ่งงานย่อย ไม่รวมงานหลายอย่างในไฟล์เดียว write true
04_SYNTHESIS/ รวบรวมและจัดระเบียบผลลัพธ์จาก 03_WORK_PACKAGES เชื่อมโยงข้อมูล เรียงลำดับ จัดกลุ่ม ห้ามเติมข้อมูลใหม่หรือตีความเพิ่มเติม หากพบช่องว่างระหว่างข้อมูล ให้ระบุสถานะ MISSING พร้อมระบุส่วนที่ขาดอย่างชัดเจน append true
05_REVIEW/ บันทึกผลการตรวจสอบแยกออกจากพื้นที่ทำงาน แยกเป็น 3 ประเภท: PASS / REVIEW_ISSUES / INSUFFICIENT_EVIDENCE ผู้ตรวจต้องเป็นบุคคลหรือกระบวนการที่แยกต่างหากจากผู้ดำเนินงาน ห้ามตรวจงานของตนเอง write true
06_RELEASE/ เก็บเฉพาะผลงานฉบับสมบูรณ์ที่ผ่านการตรวจสอบและได้รับการอนุมัติแล้วเท่านั้น บันทึกเลขที่อนุมัติ วันที่ และหมายเลขรุ่น เมื่อย้ายมาแล้ว ห้ามแก้ไขเนื้อหา สิทธิ์อ่านอย่างเดียว ยกเว้นการย้ายเวอร์ชันใหม่ที่ได้รับอนุมัติ readonly true
99_ARCHIVE/ เก็บรุ่นเก่า ฉบับที่ถูกแทนที่ และงานที่ระงับ ด้วยเหตุผลใดๆ พร้อมบันทึกเหตุผลที่ย้ายมาและวันที่ ห้ามลบถาวร ย้ายมาที่นี่ได้อย่างเดียว ไม่ใช่พื้นที่ทำงานปัจจุบัน archived true

2. คำจำกัดความสถานะ

รหัสสถานะ ความหมาย การดำเนินการที่ต้องปฏิบัติ
CONFIRMED มีหลักฐานยืนยันจากแหล่งที่น่าเชื่อถือ ข้อมูลชัดเจนครบถ้วน อ้างอิงแหล่งที่มา ใช้งานได้
UNKNOWN มีช่องว่างหรือข้อมูลไม่ครบถ้วน ไม่สามารถระบุได้ชัดเจน แต่ทราบว่าขาดส่วนไหน ระบุรายการที่ขอข้อมูลเพิ่ม อย่าสมมติค่าเติมเข้าไป
NOT_FOUND ตรวจสอบแหล่งที่มาที่มีแล้ว แต่ไม่พบข้อมูลที่เกี่ยวข้อง ระบุรายการแหล่งที่ตรวจสอบแล้ว และผลลัพธ์ที่ได้ อย่าสรุปว่าไม่มีอยู่จริงทั่วโลก
MISSING ข้อมูลหรือผลงานส่วนก่อนหน้ายังไม่มี ไม่สามารถดำเนินงานส่วนถัดไปได้ บันทึกสิ่งที่ขาด หยุดงานชั่วคราว แจ้งผู้เกี่ยวข้อง
BLOCKED หยุดการดำเนินงานชั่วคราวด้วยเหตุผลที่ยืนยันได้ เช่น รอข้อมูล รออนุมัติ หรือรอผลงานส่วนอื่น ระบุสาเหตุที่ชัดเจน รายการสิ่งที่ต้องได้รับก่อนดำเนินต่อ และสถานะงานที่พึ่งพา
PASS ผลงานตรงตามเกณฑ์ มีหลักฐานครบถ้วน ถูกต้อง ผ่านการตรวจสอบ ย้ายไป 06_RELEASE ตามขั้นตอน บันทึกเลขที่อนุมัติและวันที่
REVIEW_ISSUES ผลงานมีจุดที่ต้องแก้ไขหรือปรับปรุง แต่โครงสร้างโดยรวมสมบูรณ์ ระบุจุดที่ต้องแก้ไข ข้อเสนอแนะ และส่งกลับไปยัง 03_WORK_PACKAGES
INSUFFICIENT_EVIDENCE ดำเนินงานตามที่มีแล้ว แต่หลักฐานไม่เพียงพอที่จะยืนยันความถูกต้องของผลลัพธ์ ระบุรายการหลักฐานที่ขาด ห้ามสรุปผลในส่วนที่ยังไม่มีการยืนยัน

หมายเหตุ v1.1: ดู Decision Tree การเลือกสถานะได้ที่ ส่วนที่ 9 เพื่อลดความสับสนระหว่าง UNKNOWN / NOT_FOUND / MISSING / BLOCKED

3. รูปแบบเอกสารงาน (Schema)

หมายเหตุ v1.1: ทุก schema มีการเพิ่มฟิลด์ "schemaVersion" เพื่อระบุเวอร์ชันของ schema ที่ใช้ — ช่วยให้ตรวจสอบย้อนหลังได้ว่าเอกสารใดใช้ schema รุ่นใด

4. ขั้นตอนการปฏิบัติงาน

ขั้นที่ ชื่อขั้นตอน การดำเนินการ บันทึกที่ ส่งต่อไปที่
1 รับโจทย์ → บันทึก TaskDocument กำหนด TASK-ID (YYYYMMDD-XXX); บันทึกคำผู้ใช้ตรงๆ; ระบุขอบเขต/แหล่งที่มา/สิ่งที่ขาด 01_INBOX/ → ย้ายไป 03_WORK_PACKAGES/ 03_WORK_PACKAGES/
2 ดำเนินงานตามขอบเขต ใช้เฉพาะข้อมูลที่มีแหล่งอ้างอิง; ทุกข้อมูลระบุสถานะ; พบช่องว่าง → UNKNOWN/MISSING; แบ่งงานขนานหรือลำดับตามความพึ่งพา 03_WORK_PACKAGES/TASK-ID.md 04_SYNTHESIS/
3 รวบรวม → เขียน ProgressReport → ส่งตรวจ รวบรวมจาก 03 เท่านั้น; ห้ามเติมข้อมูล; เชื่อมโยงข้อมูล; สร้างรายงาน; ส่งพร้อมอ้างอิงทั้งหมด 04_SYNTHESIS/TASK-ID-report.md 05_REVIEW/
4 ตรวจสอบ → บันทึก ReviewRecord → จัดส่ง ผู้ตรวจต้องไม่ใช่ผู้ทำงาน; ตรวจความครบถ้วน/หลักฐาน; บันทึกผล; ผ่าน → ย้ายไป 06_RELEASE; มีปัญหา → ส่งกลับ 03 05_REVIEW/TASK-ID-review.md 06_RELEASE/ หรือ 03_WORK_PACKAGES/

รายละเอียดแต่ละขั้นตอน

ขั้นที่ 1: ก่อนเริ่มงาน

  • กำหนดรหัสงานในรูปแบบ YYYYMMDD-XXX ตัวอย่าง: 20261025-001
  • บันทึกข้อความต้นฉบับจากผู้ใช้โดยตรง ห้ามแก้ไข ถอดความ หรือปรับปรุงถ้อยคำ
  • ระบุวัตถุประสงค์อย่างชัดเจน แยกสิ่งที่ต้องทำและสิ่งที่ไม่อยู่ในขอบเขต
  • รายการแหล่งข้อมูลที่มีอยู่และสถานะความพร้อมใช้งาน
  • ระบุผลลัพธ์ที่คาดหวังและเกณฑ์การยอมรับ
  • บันทึกงานที่ต้องรอผลจากส่วนอื่น
  • ระบุรายการสิ่งที่ยังไม่ทราบหรือข้อมูลที่ขาด พร้อมสถานะ

ขั้นที่ 2: ดำเนินงาน

  • ใช้เฉพาะข้อมูลที่มีแหล่งอ้างอิงใน 02_EVIDENCE หรือแหล่งที่ระบุไว้ชัดเจน
  • ทุกข้อความที่ไม่ใช่ความเห็นของผู้ปฏิบัติงานต้องมีการอ้างอิงแหล่งที่มา
  • หากพบข้อมูลไม่ครบถ้วนหรือไม่สามารถยืนยันได้ ให้ระบุสถานะทันที ห้ามสมมติหรือเติมข้อมูลเพื่อความสมบูรณ์
  • แบ่งงานย่อยตามความเหมาะสม: งานที่ไม่ต้องอาศัยข้อมูลจากส่วนอื่นสามารถดำเนินงานขนานกันได้ งานที่ต้องใช้ผลลัพธ์จากส่วนก่อนหน้า ให้ระบุสถานะ MISSING หรือ BLOCKED แล้วหยุดชั่วคราว
  • ผู้ประสานงานรวบรวมผลลัพธ์ ตรวจสอบความครบถ้วน และส่งต่อ ไม่จำเป็นต้องแยกเป็นหลายหน่วยงานในทุกกรณี

ขั้นที่ 3: รวบรวมและส่งตรวจ

  • รวบรวมผลลัพธ์จาก 03_WORK_PACKAGES เท่านั้น
  • จัดระเบียบ เชื่อมโยง และเรียงลำดับข้อมูล
  • ห้ามตีความหรือสรุปในส่วนที่ไม่มีหลักฐานสนับสนุน
  • สร้างรายงานความก้าวหน้าตามรูปแบบ ProgressReport
  • ส่งไปยัง 05_REVIEW พร้อมเอกสารอ้างอิงทั้งหมด

ขั้นที่ 4: ตรวจสอบและอนุมัติ

  • ผู้ตรวจต้องเป็นบุคคลหรือกระบวนการที่แยกต่างหากจากผู้ดำเนินงาน
  • ตรวจสอบความถูกต้อง ความครบถ้วน และการมีหลักฐานสนับสนุน
  • บันทึกผลการตรวจตามรูปแบบ ReviewRecord
  • PASS: ย้ายสำเนาไปยัง 06_RELEASE เก็บต้นฉบับที่เดิม
  • REVIEW_ISSUES: บันทึกจุดที่ต้องแก้ไข ส่งกลับไปยัง 03_WORK_PACKAGES พร้อมคำอธิบาย
  • INSUFFICIENT_EVIDENCE: บันทึกรายการหลักฐานที่ต้องการเพิ่มเติม ไม่อนุมัติ จนกว่าจะได้รับข้อมูลครบถ้วน

5. ข้อห้ามและหลักการพื้นฐาน

รหัสกฎ หลักการ สิ่งที่ห้ามปฏิบัติ สิ่งที่ต้องปฏิบัติแทน
RULE-001 ห้ามสรุปจากความจำโดยไม่มีแหล่งอ้างอิง อ้างว่า "จำได้ว่า", "เคยพูดกันว่า", หรือสรุปเนื้อหาโดยไม่ระบุเอกสารอ้างอิง อ้างอิงชื่อไฟล์ ตำแหน่ง และวันที่ทุกครั้ง หากไม่มีแหล่งให้ระบุสถานะ NOT_FOUND
RULE-002 ห้ามเขียนทับต้นฉบับ แก้ไข ปรับปรุง หรือลดข้อความที่บันทึกเป็นต้นฉบับ บันทึกฉบับใหม่เพิ่มเข้าไป พร้อมระบุวันที่และรุ่น ย้ายฉบับเก่าไปที่ 99_ARCHIVE
RULE-003 ห้ามเติมข้อมูลเพื่อความสมบูรณ์ ใช้ถ้อยคำเช่น "น่าจะเป็น", "คาดว่า", "โดยสรุปแล้ว" ในส่วนที่ไม่มีหลักฐาน ระบุสถานะ UNKNOWN หรือ NOT_FOUND พร้อมคำอธิบายว่าทราบเท่าที่มีข้อมูลเท่านั้น
RULE-004 ห้ามปฏิเสธงานโดยไม่มีเหตุผล ตั้งสถานะ BLOCKED ด้วยเหตุผล "ไม่เกี่ยวข้อง" หรือ "ไม่ใช่งานของส่วนนี้" ระบุสาเหตุที่ตรวจสอบยืนยันได้ เช่น ขาดข้อมูล รออนุมัติ หรือรอผลงานส่วนอื่น พร้อมรายการสิ่งที่ต้องการ
RULE-005 ห้ามตรวจงานตัวเอง รับรองหรือยืนยันความถูกต้องของผลงานที่ตนเองเป็นผู้จัดทำ ส่งงานไปยังกระบวนการตรวจสอบที่แยกต่างหาก บุคคลหรือระบบที่ทำหน้าที่ตรวจสอบต้องไม่ใช่ผู้ปฏิบัติงาน
RULE-006 ห้ามลบประวัติ ลบเอกสารหรือข้อมูลที่เคยบันทึกแล้ว ย้ายไฟล์ไปยัง 99_ARCHIVE พร้อมบันทึกเหตุผลและวันที่ย้าย

ข้อสังเกต v1.1 — การบังคับใช้กฎเชิงกลไก: กฎ RULE-001 และ RULE-003 ต้องอาศัยวินัยของผู้ปฏิบัติ (หรือ AI) เป็นหลัก เพื่อลดความเสี่ยงจาก hallucination ควรใช้ Self-check prompt (ดูส่วนที่ 11) ทุกครั้งก่อนส่งงาน และตรวจว่า sourceRef ครบทุกข้อความ

6. Glossary คำศัพท์ ใหม่ v1.1

คำศัพท์ไทย-อังกฤษที่ใช้ในเอกสารนี้ เพื่อลดความกำกวม

คำศัพท์ ความหมายในบริบทนี้ หมายเหตุ
TaskDocument เอกสารบันทึกโจทย์และขอบเขตงาน ก่อนเริ่มดำเนินงาน Schema 1
ProgressReport รายงานความก้าวหน้าและผลลัพธ์ที่ทำเสร็จ Schema 2
ReviewRecord บันทึกผลการตรวจสอบและอนุมัติ Schema 3
Source reference การอ้างอิงแหล่งที่มาของข้อมูล (ไฟล์ ตำแหน่ง วันที่) จำเป็นต่อการตรวจสอบย้อนกลับ
Provenance ที่มาและประวัติของข้อมูล ใช้ในบริบทของ 02_EVIDENCE
Append-only การบันทึกแบบเพิ่มอย่างเดียว ไม่แก้ไขหรือลบ ใช้กับ 01_INBOX, 02_EVIDENCE, 04_SYNTHESIS
Maker-checker หลักการแยกผู้ทำและผู้ตรวจ อ้างอิง RULE-005
Escalation การยกระดับปัญหาหรือส่งต่อผู้มีอำนาจตัดสินใจ ดูส่วนที่ 10
RACI Responsible / Accountable / Consulted / Informed ดูส่วนที่ 7
BLOCKED สถานะหยุดชั่วคราวด้วยเหตุผลที่ยืนยันได้ ไม่ใช่การปฏิเสธงาน

7. ผู้รับผิดชอบและสิทธิ์การอนุมัติ (RACI) ใหม่ v1.1

ตารางแสดงบทบาทความรับผิดชอบตามไดเรกทอรี (R = ผู้ปฏิบัติ, A = ผู้รับผิดชอบสูงสุด/อนุมัติ, C = ผู้ให้คำปรึกษา, I = ผู้รับทราบ)

ไดเรกทอรี / กิจกรรม ผู้ปฏิบัติ (R) ผู้อนุมัติ (A) ผู้ให้คำปรึกษา (C) ผู้รับทราบ (I)
00_CONTROL/ ผู้ดูแลระบบ (Admin) ผู้บริหารโครงการ (PM) ทีมกำกับดูแล ทุกทีม
01_INBOX/ ผู้รับงาน — — ผู้ประสานงาน
02_EVIDENCE/ นักวิจัย/ผู้สืบค้น หัวหน้าทีมวิจัย ผู้เชี่ยวชาญเฉพาะด้าน ผู้ประสานงาน
03_WORK_PACKAGES/ ผู้ปฏิบัติงานย่อย หัวหน้างานย่อย — ผู้ประสานงาน
04_SYNTHESIS/ ผู้สังเคราะห์ หัวหน้าทีมสังเคราะห์ ผู้ตรวจสอบ ผู้ประสานงาน
05_REVIEW/ ผู้ตรวจสอบ ผู้อนุมัติ (แยกจากผู้ทำ) — ผู้บริหารโครงการ

99_ARCHIVE/ ผู้ดูแลระบบ ผู้บริหารโครงการ — ทุกทีม

9. Decision Tree สำหรับเลือกสถานะ ใหม่ v1.1

ใช้แผนภาพนี้เพื่อตัดสินใจเลือกสถานะให้ถูกต้องเมื่อพบความไม่สมบูรณ์ของข้อมูล

เริ่ม: ข้อมูล/ผลงานไม่สมบูรณ์
│
├─ ตรวจสอบแหล่งข้อมูลที่มีอยู่แล้วหรือไม่?
│   │
│   ├─ ไม่ได้ตรวจสอบ → ต้องตรวจสอบก่อน (ห้ามสรุป)
│   │
│   └─ ตรวจสอบแล้ว
│       │
│       ├─ พบข้อมูลแต่ยังไม่ครบถ้วน → UNKNOWN
│       │     (ระบุว่าขาดส่วนไหน)
│       │
│       ├─ ไม่พบข้อมูลในแหล่งที่ตรวจ → NOT_FOUND
│       │     (ระบุแหล่งที่ตรวจแล้ว)
│       │
│       └─ ข้อมูลส่วนก่อนหน้ายังไม่มี → MISSING
│             (หยุดงานชั่วคราว)
│
└─ มีเหตุให้หยุดชั่วคราวที่ยืนยันได้หรือไม่?
    │
    ├─ รอข้อมูล/รออนุมัติ/รอผลงานอื่น → BLOCKED
    │     (ระบุสิ่งที่ต้องได้รับก่อนดำเนินต่อ)
    │
    └─ ไม่มีเหตุ → ดำเนินงานต่อด้วยข้อมูลที่มี
          (ห้ามเติมข้อมูลเอง)
สถานะ เงื่อนไขหลัก สิ่งที่ต้องระบุเพิ่ม
UNKNOWN พบข้อมูลแต่ไม่ครบ รู้ว่าขาดอะไร รายการที่ขาด + คำขอข้อมูล
NOT_FOUND ตรวจแหล่งแล้วไม่พบ รายชื่อแหล่งที่ตรวจ + วันที่เข้าถึง
MISSING ผลงานส่วนก่อนหน้ายังไม่มี ส่วนที่ขาด + TASK-ID ที่ต้องรอ
BLOCKED หยุดชั่วคราวด้วยเหตุที่ยืนยันได้ สาเหตุ + สิ่งที่ต้องได้รับก่อนดำเนินต่อ

10. Escalation & Backup Policy ใหม่ v1.1

10.1 Escalation Path

หากงานอยู่ในสถานะ BLOCKED หรือ MISSING เกินระยะเวลาที่กำหนด ให้ดำเนินการยกระดับดังนี้

ระยะเวลา การดำเนินการ ผู้รับผิดชอบ
≤ 2 วันทำการ ผู้ปฏิบัติติดตามสถานะและบันทึกใน TaskDocument ผู้ปฏิบัติงาน
3–5 วันทำการ แจ้งหัวหน้างานย่อย + บันทึกเหตุผลใน ProgressReport หัวหน้างานย่อย
6–10 วันทำการ ยกระดับถึงผู้บริหารโครงการ + พิจารณาทางเลือกทดแทน ผู้บริหารโครงการ
> 10 วันทำการ พิจารณาระงับงาน → ย้ายไป 99_ARCHIVE พร้อมบันทึกเหตุผล ผู้บริหารโครงการ

10.2 Backup Policy

  • GitHub repository ทำหน้าที่เป็น primary backup — ต้องมี remote สำรองอย่างน้อย 1 แห่ง
  • สำรองข้อมูลเต็มรูปแบบ (full backup) อย่างน้อยเดือนละ 1 ครั้ง
  • ตรวจสอบความสามารถในการ restore ทุกไตรมาส
  • ห้ามลบ backup แม้แต่งานจะถูก archive แล้ว (ตาม RULE-006)

10.3 Conflict Resolution (Concurrent Editing)

  • หนึ่งไฟล์ใน 03_WORK_PACKAGES/ ต้องมีเจ้าของไฟล์เดียว (single owner) ณ เวลาหนึ่ง
  • หากต้องทำงานขนาน ให้แยกเป็น TASK-ID ใหม่ ไม่แก้ไฟล์เดิม
  • ก่อนแก้ไฟล์ ให้ pull ล่าสุดและตรวจสอบ version ก่อน push
  • หากเกิด conflict ใน 04_SYNTHESIS/ ให้ผู้ประสานงานเป็นผู้ตัดสินและบันทึกเหตุผล

Self-check Prompt (ใหม่ v1.1)

ก่อนส่งงานทุกครั้ง ให้ AI ตรวจสอบตัวเองด้วยคำถามต่อไปนี้

  1. ทุกข้อความใน ProgressReport มี sourceRef ครบหรือไม่?
  2. มีข้อความใดที่ใช้ถ้อยคำ "น่าจะ", "คาดว่า", "โดยสรุป" ในส่วนที่ไม่มีหลักฐานหรือไม่? (หากมี → เปลี่ยนเป็น UNKNOWN/NOT_FOUND)
  3. สถานะที่ใช้ตรงกับ Decision Tree (ส่วนที่ 9) หรือไม่?
  4. ชื่อไฟล์ตรงตาม Naming Convention (ส่วนที่ 8) หรือไม่?
  5. ได้บันทึก schemaVersion ในเอกสารแล้วหรือไม่?
  6. มีข้อมูลใดที่ "เติมเอง" เพื่อให้ดูสมบูรณ์หรือไม่? (หากมี → ลบออกและระบุสถานะ)

  1. บันทึก: คัดลอกโค้ดทั้งหน้านี้ → บันทึกเป็นไฟล์ชื่อ: project-workflow-manual-v1.1.html

  3. ใช้กับ AI: เปิดไฟล์นี้ในเบราว์เซอร์ → คัดเนื้อหาส่วนที่ต้องการ → วางใน ChatGPT Project Instructions หรือส่งให้ AI อ่าน
