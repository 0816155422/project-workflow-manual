1. โครงสร้างพื้นที่จัดเก็บ

หลักการ: ต้นฉบับไม่เคยถูกเขียนทับ → เพิ่มรุ่นใหม่เมื่อมีการเปลี่ยน → เก็บทุกเวอร์ชัน ไม่ลบ

ไดเรกทอรี วัตถุประสงค์ กฎการใช้งาน สิทธิ์เขียน เก็บรุ่น
00_CONTROL/กติกากลาง, แบบฟอร์ม, คำจำกัดความสถานะ, ขั้นตอนมาตรฐานระบบอ่านอย่างเดียว — ห้ามแก้ไขโดยไม่มีการอนุมัติและบันทึกเหตุผลreadonlytrue
01_INBOX/บันทึกโจทย์ผู้ใช้ตามถ้อยคำเดิม; เก็บไฟล์และเอกสารต้นฉบับที่ได้รับคัดลอกข้อความตรงตัว ห้ามแก้ไข ตีความ หรือสรุปแทนเจ้าของข้อความ บันทึกเวลาและแหล่งที่มาทุกรายการappendtrue
02_EVIDENCE/เก็บข้อมูลดิบ ผลสืบค้น เนื้อหาเอกสารต้นฉบับ พร้อมแหล่งอ้างอิง รุ่น และวันที่เข้าถึงข้อมูลทุกรายการต้องระบุแหล่งที่มา รุ่นหรือหมายเลขฉบับ และวันที่ หากไม่มีแหล่งอ้างอิงที่ยืนยันได้ ให้ระบุสถานะ NOT_FOUNDappendtrue
03_WORK_PACKAGES/แยกเก็บงานย่อยตามส่วนงาน แต่ละรายการประกอบด้วยรหัสงาน โจทย์ย่อย รายการที่ต้องทำ ผลลัพธ์ระหว่างทาง และปัญหาที่พบทุกไฟล์ต้องมีรหัสงานกำกับ หนึ่งไฟล์ต่อหนึ่งงานย่อย ไม่รวมงานหลายอย่างในไฟล์เดียวwritetrue
04_SYNTHESIS/รวบรวมและจัดระเบียบผลลัพธ์จาก 03_WORK_PACKAGES เชื่อมโยงข้อมูล เรียงลำดับ จัดกลุ่มห้ามเติมข้อมูลใหม่หรือตีความเพิ่มเติม หากพบช่องว่างระหว่างข้อมูล ให้ระบุสถานะ MISSING พร้อมระบุส่วนที่ขาดอย่างชัดเจนappendtrue
05_REVIEW/บันทึกผลการตรวจสอบแยกออกจากพื้นที่ทำงาน แยกเป็น 3 ประเภท: PASS / REVIEW_ISSUES / INSUFFICIENT_EVIDENCEผู้ตรวจต้องเป็นบุคคลหรือกระบวนการที่แยกต่างหากจากผู้ดำเนินงาน ห้ามตรวจงานของตนเองwritetrue
06_RELEASE/เก็บเฉพาะผลงานฉบับสมบูรณ์ที่ผ่านการตรวจสอบและได้รับการอนุมัติแล้วเท่านั้น บันทึกเลขที่อนุมัติ วันที่ และหมายเลขรุ่นเมื่อย้ายมาแล้ว ห้ามแก้ไขเนื้อหา สิทธิ์อ่านอย่างเดียว ยกเว้นการย้ายเวอร์ชันใหม่ที่ได้รับอนุมัติreadonlytrue
99_ARCHIVE/เก็บรุ่นเก่า ฉบับที่ถูกแทนที่ และงานที่ระงับ ด้วยเหตุผลใดๆ พร้อมบันทึกเหตุผลที่ย้ายมาและวันที่ห้ามลบถาวร ย้ายมาที่นี่ได้อย่างเดียว ไม่ใช่พื้นที่ทำงานปัจจุบันarchivedtrue

2. คำจำกัดความสถานะ

รหัสสถานะความหมายการดำเนินการที่ต้องปฏิบัติ
CONFIRMEDมีหลักฐานยืนยันจากแหล่งที่น่าเชื่อถือ ข้อมูลชัดเจนครบถ้วนอ้างอิงแหล่งที่มา ใช้งานได้
UNKNOWNมีช่องว่างหรือข้อมูลไม่ครบถ้วน ไม่สามารถระบุได้ชัดเจน แต่ทราบว่าขาดส่วนไหนระบุรายการที่ขอข้อมูลเพิ่ม อย่าสมมติค่าเติมเข้าไป
NOT_FOUNDตรวจสอบแหล่งที่มาที่มีแล้ว แต่ไม่พบข้อมูลที่เกี่ยวข้องระบุรายการแหล่งที่ตรวจสอบแล้ว และผลลัพธ์ที่ได้ อย่าสรุปว่าไม่มีอยู่จริงทั่วโลก
MISSINGข้อมูลหรือผลงานส่วนก่อนหน้ายังไม่มี ไม่สามารถดำเนินงานส่วนถัดไปได้บันทึกสิ่งที่ขาด หยุดงานชั่วคราว แจ้งผู้เกี่ยวข้อง
BLOCKEDหยุดการดำเนินงานชั่วคราวด้วยเหตุผลที่ยืนยันได้ เช่น รอข้อมูล รออนุมัติ หรือรอผลงานส่วนอื่นระบุสาเหตุที่ชัดเจน รายการสิ่งที่ต้องได้รับก่อนดำเนินต่อ และสถานะงานที่พึ่งพา
PASSผลงานตรงตามเกณฑ์ มีหลักฐานครบถ้วน ถูกต้อง ผ่านการตรวจสอบย้ายไป 06_RELEASE ตามขั้นตอน บันทึกเลขที่อนุมัติและวันที่
REVIEW_ISSUESผลงานมีจุดที่ต้องแก้ไขหรือปรับปรุง แต่โครงสร้างโดยรวมสมบูรณ์ระบุจุดที่ต้องแก้ไข ข้อเสนอแนะ และส่งกลับไปยัง 03_WORK_PACKAGES
INSUFFICIENT_EVIDENCEดำเนินงานตามที่มีแล้ว แต่หลักฐานไม่เพียงพอที่จะยืนยันความถูกต้องของผลลัพธ์ระบุรายการหลักฐานที่ขาด ห้ามสรุปผลในส่วนที่ยังไม่มีการยืนยัน

4. ขั้นตอนการปฏิบัติงาน

ขั้นที่ชื่อขั้นตอนการดำเนินการบันทึกที่ส่งต่อไปที่
1รับโจทย์ → บันทึก TaskDocumentกำหนด TASK-ID (YYYYMMDD-XXX); บันทึกคำผู้ใช้ตรงๆ; ระบุขอบเขต/แหล่งที่มา/สิ่งที่ขาด01_INBOX/ → ย้ายไป 03_WORK_PACKAGES/03_WORK_PACKAGES/
2ดำเนินงานตามขอบเขตใช้เฉพาะข้อมูลที่มีแหล่งอ้างอิง; ทุกข้อมูลระบุสถานะ; พบช่องว่าง → UNKNOWN/MISSING; แบ่งงานขนานหรือลำดับตามความพึ่งพา03_WORK_PACKAGES/TASK-ID.md04_SYNTHESIS/
3รวบรวม → เขียน ProgressReport → ส่งตรวจรวบรวมจาก 03 เท่านั้น; ห้ามเติมข้อมูล; เชื่อมโยงข้อมูล; สร้างรายงาน; ส่งพร้อมอ้างอิงทั้งหมด04_SYNTHESIS/TASK-ID-report.md05_REVIEW/
4ตรวจสอบ → บันทึก ReviewRecord → จัดส่งผู้ตรวจต้องไม่ใช่ผู้ทำงาน; ตรวจความครบถ้วน/หลักฐาน; บันทึกผล; ผ่าน → ย้ายไป 06_RELEASE; มีปัญหา → ส่งกลับ 0305_REVIEW/TASK-ID-review.md06_RELEASE/ หรือ 03_WORK_PACKAGES/

รายละเอียดแต่ละขั้นตอน

ขั้นที่ 1: ก่อนเริ่มงาน

  • กำหนดรหัสงานในรูปแบบ YYYYMMDD-XXX
  • บันทึกข้อความต้นฉบับจากผู้ใช้โดยตรง ห้ามแก้ไข ถอดความ หรือปรับปรุงถ้อยคำ
  • ระบุวัตถุประสงค์อย่างชัดเจน แยกสิ่งที่ต้องทำและสิ่งที่ไม่อยู่ในขอบเขต
  • รายการแหล่งข้อมูลที่มีอยู่และสถานะความพร้อมใช้งาน
  • ระบุผลลัพธ์ที่คาดหวังและเกณฑ์การยอมรับ
  • บันทึกงานที่ต้องรอผลจากส่วนอื่น
  • ระบุรายการสิ่งที่ยังไม่ทราบหรือข้อมูลที่ขาด พร้อมสถานะ

ขั้นที่ 2: ดำเนินงาน

  • ใช้เฉพาะข้อมูลที่มีแหล่งอ้างอิงใน 02_EVIDENCE หรือแหล่งที่ระบุไว้ชัดเจน
  • ทุกข้อความที่ไม่ใช่ความเห็นของผู้ปฏิบัติงานต้องมีการอ้างอิงแหล่งที่มา
  • หากพบข้อมูลไม่ครบถ้วนหรือไม่สามารถยืนยันได้ ให้ระบุสถานะทันที
  • แบ่งงานย่อยตามความเหมาะสม: งานที่ไม่ต้องอาศัยข้อมูลจากส่วนอื่นสามารถดำเนินงานขนานกันได้
  • ผู้ประสานงานรวบรวมผลลัพธ์ ตรวจสอบความครบถ้วน และส่งต่อ

ขั้นที่ 3: รวบรวมและส่งตรวจ

  • รวบรวมผลลัพธ์จาก 03_WORK_PACKAGES เท่านั้น
  • จัดระเบียบ เชื่อมโยง และเรียงลำดับข้อมูล
  • ห้ามตีความหรือสรุปในส่วนที่ไม่มีหลักฐานสนับสนุน
  • สร้างรายงานความก้าวหน้าตามรูปแบบ ProgressReport
  • ส่งไปยัง 05_REVIEW พร้อมเอกสารอ้างอิงทั้งหมด

ขั้นที่ 4: ตรวจสอบและอนุมัติ

  • ผู้ตรวจต้องเป็นบุคคลหรือกระบวนการที่แยกต่างหากจากผู้ดำเนินงาน
  • ตรวจสอบความถูกต้อง ความครบถ้วน และการมีหลักฐานสนับสนุน
  • บันทึกผลการตรวจตามรูปแบบ ReviewRecord
  • PASS: ย้ายสำเนาไปยัง 06_RELEASE เก็บต้นฉบับที่เดิม
  • REVIEW_ISSUES: บันทึกจุดที่ต้องแก้ไข ส่งกลับไปยัง 03_WORK_PACKAGES
  • INSUFFICIENT_EVIDENCE: บันทึกรายการหลักฐานที่ต้องการเพิ่มเติม

5. ข้อห้ามและหลักการพื้นฐาน

รหัสกฎหลักการสิ่งที่ห้ามปฏิบัติสิ่งที่ต้องปฏิบัติแทน
RULE-001ห้ามสรุปจากความจำโดยไม่มีแหล่งอ้างอิงอ้างว่า "จำได้ว่า", "เคยพูดกันว่า" หรือสรุปเนื้อหาโดยไม่ระบุเอกสารอ้างอิงอ้างอิงชื่อไฟล์ ตำแหน่ง และวันที่ทุกครั้ง หากไม่มีแหล่งให้ระบุสถานะ NOT_FOUND
RULE-002ห้ามเขียนทับต้นฉบับแก้ไข ปรับปรุง หรือลดข้อความที่บันทึกเป็นต้นฉบับบันทึกฉบับใหม่เพิ่มเข้าไป พร้อมระบุวันที่และรุ่น ย้ายฉบับเก่าไปที่ 99_ARCHIVE
RULE-003ห้ามเติมข้อมูลเพื่อความสมบูรณ์ใช้ถ้อยคำเช่น "น่าจะเป็น", "คาดว่า", "โดยสรุปแล้ว" ในส่วนที่ไม่มีหลักฐานระบุสถานะ UNKNOWN หรือ NOT_FOUND พร้อมคำอธิบายว่าทราบเท่าที่มีข้อมูลเท่านั้น
RULE-004ห้ามปฏิเสธงานโดยไม่มีเหตุผลตั้งสถานะ BLOCKED ด้วยเหตุผล "ไม่เกี่ยวข้อง" หรือ "ไม่ใช่งานของส่วนนี้"ระบุสาเหตุที่ตรวจสอบยืนยันได้ เช่น ขาดข้อมูล รออนุมัติ หรือรอผลงานส่วนอื่น พร้อมรายการสิ่งที่ต้องการ
RULE-005ห้ามตรวจงานตัวเองรับรองหรือยืนยันความถูกต้องของผลงานที่ตนเองเป็นผู้จัดทำส่งงานไปยังกระบวนการตรวจสอบที่แยกต่างหาก
RULE-006ห้ามลบประวัติลบเอกสารหรือข้อมูลที่เคยบันทึกแล้วย้ายไฟล์ไปยัง 99_ARCHIVE พร้อมบันทึกเหตุผลและวันที่ย้าย

6. Glossary คำศัพท์ v1.1

  • TaskDocument: เอกสารบันทึกโจทย์และขอบเขตงาน ก่อนเริ่มดำเนินงาน
  • ProgressReport: รายงานความก้าวหน้าและผลลัพธ์ที่ทำเสร็จ
  • ReviewRecord: บันทึกผลการตรวจสอบและอนุมัติ
  • Source reference: การอ้างอิงแหล่งที่มาของข้อมูล
  • Provenance: ที่มาและประวัติของข้อมูล
  • Append-only: การบันทึกแบบเพิ่มอย่างเดียว ไม่แก้ไขหรือลบ
  • Maker-checker: หลักการแยกผู้ทำและผู้ตรวจ
  • Escalation: การยกระดับปัญหาหรือส่งต่อผู้มีอำนาจตัดสินใจ
  • RACI: Responsible / Accountable / Consulted / Informed

9. Decision Tree สถานะ v1.1

เริ่ม: ข้อมูล/ผลงานไม่สมบูรณ์
│
├─ ตรวจสอบแหล่งข้อมูลที่มีอยู่แล้วหรือไม่?
│   │
│   ├─ ไม่ได้ตรวจสอบ → ต้องตรวจสอบก่อน (ห้ามสรุป)
│   │
│   └─ ตรวจสอบแล้ว
│       │
│       ├─ พบข้อมูลแต่ยังไม่ครบถ้วน → UNKNOWN
│       │
│       ├─ ไม่พบข้อมูลในแหล่งที่ตรวจ → NOT_FOUND
│       │
│       └─ ข้อมูลส่วนก่อนหน้ายังไม่มี → MISSING
│
└─ มีเหตุให้หยุดชั่วคราวที่ยืนยันได้หรือไม่?
    │
    ├─ รอข้อมูล/รออนุมัติ/รอผลงานอื่น → BLOCKED
    │
    └─ ไม่มีเหตุ → ดำเนินงานต่อด้วยข้อมูลที่มี

UNKNOWN: พบข้อมูลแต่ไม่ครบ รู้ว่าขาดอะไร

NOT_FOUND: ตรวจแหล่งแล้วไม่พบ

MISSING: ผลงานส่วนก่อนหน้ายังไม่มี

BLOCKED: หยุดชั่วคราวด้วยเหตุที่ยืนยันได้

10. Escalation & Backup Policy v1.1

10.1 Escalation Path

ระยะเวลาการดำเนินการผู้รับผิดชอบ
≤ 2 วันทำการผู้ปฏิบัติติดตามสถานะและบันทึกใน TaskDocumentผู้ปฏิบัติงาน
3–5 วันทำการแจ้งหัวหน้างานย่อย + บันทึกเหตุผลใน ProgressReportหัวหน้างานย่อย
6–10 วันทำการยกระดับถึงผู้บริหารโครงการ + พิจารณาทางเลือกทดแทนผู้บริหารโครงการ
> 10 วันทำการพิจารณาระงับงาน → ย้ายไป 99_ARCHIVE พร้อมบันทึกเหตุผลผู้บริหารโครงการ

10.2 Backup Policy

  • GitHub repository ทำหน้าที่เป็น primary backup — ต้องมี remote สำรองอย่างน้อย 1 แห่ง
  • สำรองข้อมูลเต็มรูปแบบ (full backup) อย่างน้อยเดือนละ 1 ครั้ง
  • ตรวจสอบความสามารถในการ restore ทุกไตรมาส
  • ห้ามลบ backup แม้แต่งานจะถูก archive แล้ว

10.3 Conflict Resolution

  • หนึ่งไฟล์ใน 03_WORK_PACKAGES/ ต้องมีเจ้าของไฟล์เดียว
  • หากต้องทำงานขนาน ให้แยกเป็น TASK-ID ใหม่ ไม่แก้ไฟล์เดิม
  • ก่อนแก้ไฟล์ ให้ pull ล่าสุดและตรวจสอบ version ก่อน push
  • หากเกิด conflict ใน 04_SYNTHESIS/ ให้ผู้ประสานงานเป็นผู้ตัดสินและบันทึกเหตุผล
